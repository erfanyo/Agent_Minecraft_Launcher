# 插件化 · 模块结构分析

> 「一切皆插件」落地前的模块划分。**核心组件保持在内核代码,不插件化**;
> 只有**非核心/可选(锦上添花)**功能才做成插件,由用户在 设置→插件 里启禁。

## 一、核心组件(不插件化,保持稳定)
这些是整个启动器的"底座",改动会影响全局,不作为插件:

| 模块 | 职责 |
|---|---|
| `version_home` | 我的实例(启动/导入) |
| `instance_manager` | 实例详情(Mod/数据包/光影/存档) |
| `resource_center` | 下载新资源(搜索/详情/下载) |
| `settings_center` | 设置中心 |
| `assistant` / `local_ai` | AI 助手(聊天/工具调用/翻译) |
| `agent_tools` / `modrinth` | 工具层 / Modrinth 数据源 |
| `craft / install / launch` | 安装/启动管线 |
| `skill_manager` | 技能系统(本身是插件的宿主,不插件化) |

## 二、非核心/可选(锦上添花)→ 适合做成插件
这些**去掉不伤核心,加了是亮点**,适合用插件方式承载、可启禁:

| 候选模块 | 现状 | 插件化思路 |
|---|---|---|
| **联机方案中心** `online_center` | 主 tab | 注册为主标签页插件(去掉也能用单机启动) |
| **Mod 依赖网络** `mod_graph`/`mod_deps` | 实例详情入口 | 注册为技能或主标签页插件 |
| **MCP 集成**(server+client) | 设置→系统 | 注册为设置页 + AI 工具插件 |
| **配色模板/可读性检查**(色盲模板) | ui_style | 注册为设置页插件(可选) |
| **崩溃诊断清单 / 本地名称归一化** 技能 | 内置 skill | 可改为"默认安装插件技能" |
| **配方旁路 / 数据新鲜度** | recipe_graph | 注册为工具插件 |

## 三、优先级建议(用户手工选择哪些做成插件)
- **第一批(价值高、改动可控)**:联机方案中心、Mod 依赖网络。
  → 这两个是"独立功能",切成插件不影响任何核心链路。
- **第二批**:MCP 集成、配色模板。
- **暂缓**:把内置 skill 全部改插件(风险大、收益一般;先保持内置,插件系统先跑通)。

## 四、怎么把一个现有功能变成插件(三步)
1. 在 `plugins/<name>.py` 声明 `PLUGIN_API_VERSION = 1` 并写 `register(api)`；使用
   `register_tool` / `register_main_tab` / `register_settings_page` / `register_skill` 注册它。
2. 原"硬接线"入口(如主编组的 addTab、左菜单 add_section)改成"若插件启用则挂载"。
3. 设置→插件 能启禁;重启生效。
