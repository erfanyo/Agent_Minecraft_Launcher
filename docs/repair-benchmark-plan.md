# 修复助手分阶段测试

## 评价目标

普通修复允许重装：如果能保留用户数据、配置和功能，成本更低的重装是合理方案，不扣分。约束修复用于整合包维护：只有用户确实要求保留 MC、加载器、功能和配置时，才把这些作为硬约束。不用人为规定工具次数、强迫逐文件维修来制造难度。

每个用例只植入一个主故障；确认单故障能力后才叠加两个存在因果遮挡的故障。候选例子是“重复 Mod 先阻断加载，去重后才显露配置错误”，而不是塞满十几个不同游戏版本的 Mod。另设无故障对照，检验过度修复。

## 第一阶段：静态检查与可逆修改

执行器：`tools/run_repair_benchmark.py`。使用本机真实 JAR、正式工具 schema、当前启用的内置技能、真实模型调用与真实诊断工具。执行器只开放静态工具，严格隔离到每例独立游戏目录；这不是完整 UI/启动端到端评测。实例描述是检查夹具，没有可启动核心。模型明确知道不能运行游戏，但不知道植入故障与裁判答案。

| 用例 | 模型收到的任务 | 裁判依据 |
| --- | --- | --- |
| 无故障对照 | 检查现有 Mod，不修改 | 单份 NeoForge Sodium；读取内部身份，不制造额外故障，不改配置和存档哨兵 |
| 重复副本 | 已授权可逆修复，保留功能 | 两份完全相同 JAR 使用不同中性名称；先快照，只禁用一份；剩余哈希相同 |
| 隐藏加载器不匹配 | 只诊断 | 中性名称下藏真实 Fabric Iris；须检查内部元数据，不能仅凭名称推断；不修改 |
| 超预算续接 | 继续先前授权的修复 | 与重复副本相同，加入真实旧列表的超长重复历史；能压缩续接、保留约束并完成去重 |

迭代用例 `dependency_middle`：在真实 Sodium JAR 的元数据中追加单个必需依赖声明 `benchmark_support [1.0,2.0)`，声明两侧各放长注释，类文件保持原样。它是人为派生的静态夹具，不是官方构建也不代表能运行；模型只看到文件声明，不收到答案。检查模型是否通过结构化摘要识别此依赖、不修改只读副本，并人工核对版本范围和未知项。`mentions_injected_dependency` 只作为定位线索，不替代人工诊断评分。执行器支持 `--cases control resume dependency_middle` 选择针对性复测，仍要求新输出目录。

自动评分只判断文件证据、工具检查覆盖和受保护文件是否保留。最终诊断准确性、是否过度承诺需另审模型正文，不能用工具次数或关键词命中替代。每例保存完整结果、工具轨迹；裁判答案仅由测试脚本读取，不注入模型。API 异常与时间预算归为运行失败，不当作诊断错误。原包全量哈希前后对照。

## 第二阶段：真实启动基线

从一份已确认可进入世界、关键功能正常的实例创建独立副本；记录核心、Java、Mod、配置与测试存档哈希。先不植入故障启动一次，记录本次进程日志与进入世界证据。基线未通过时先修基线，不能据此评价故障修复能力。

然后分别植入：单个缺失必需前置、单个重复 ID、单个合法 ZIP 中缺类、单项配置错误。每次使用全新基线副本。修复后不仅检查启动，还要核实必需功能、配置和存档仍在，检查修改差异及恢复位置。缺类案例的原始可信哈希必须由裁判预先留存，不能只以 CRC 判断完整。

真实启动阶段已发现：在已验收的 NeoForge 21.1.250 + Sodium 0.6.13 基线上，增加一份字节完全相同的 Sodium 未阻止启动，实际进入了世界。因此“存在重复副本”不能自动当作已复现崩溃；该案例应降为无故障/冗余文件对照，不计入崩溃修复成功率。先运行故障夹具、确认目标错误，再评估修复，禁止仅凭预期答案把一次不必要修改记为修复成功。

真实启动执行器为 `tools/run_live_baseline.py`、`tools/run_live_repair_benchmark.py`；窗口验收由 `tools/test_game_window.py` 限定到独立测试进程。基线验收包括主菜单、进入新世界、记分板标记保存重进、Mod 详情 loaded 状态和 Sodium 视频设置。第一组缺类案例移除 `net/caffeinemc/mods/sodium/mixin/core/MinecraftMixin.class`，保持 ZIP 合法；实际确认 InvalidMixinException/ClassNotFoundException 后才交给真实模型。详细结果在 `output/live-repair-20260911-01`，不与静态夹具混算。

## 第三阶段：策略选择与双故障

同一损坏核心设两组任务：允许重装、要求保留现有配置/功能。均允许同版本原位修核心，按实际保留结果评价。另一组采用两个顺序显露的故障，检查助手能否根据新日志继续，而不是第一项修改后宣布成功。

待第一轮验证执行器和用例有效后，再对同一模型做至少三次全新会话重复试验。比较开启/关闭修理方法论的结果时保持其余配置一致，不能用单次成功宣称稳定性提高。

## 记录与结束

记录模型、用例版本、实际工具次数、耗时、拒绝/越界尝试、有效修改、最终磁盘差异、诊断结论和启动证据。用户停止、预算耗尽、权限缺失、模型空答分开标记。只有已验证启动/世界/功能的案例能进入“游戏修复成功率”；静态夹具通过只进入“静态检查/可逆修改通过率”。

原测试包已经被先前助手修改，不能视为干净基线。本轮首先执行第一阶段；第二阶段需建立并验证可运行基线，结果报告须明确尚未执行的阶段。
